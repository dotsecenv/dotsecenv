The nice thing about personal projects is that you only have to convince yourself. When you get an itch, you scratch it.

Last weekend's itch was the dotsecenv release pipeline. Specifically: 150 lines of shell on every release that did GPG dances on a GitHub Actions runner just to sign a single commit into a satellite repo. It worked. It also looked nothing like code I wanted to maintain.

GitHub signs satellite commits through one GraphQL mutation. A custom GitHub Action handles publication across the org. Artifact and package metadata signing still use a separate GPG private key on the runners that need it.

## Why dotsecenv needs satellite repos

The dotsecenv project sits in [a mostly monorepo structure](https://github.com/dotsecenv/dotsecenv). "Mostly" because Homebrew and GitHub Pages each need their own repo:

1. [homebrew-tap](https://github.com/dotsecenv/homebrew-tap), because Homebrew expects a tap to live in its own repo at `<owner>/homebrew-<name>`.
2. [packages](https://github.com/dotsecenv/packages), because GitHub Pages publishes one site per repo. The main site is on dotsecenv.com, so the Linux and Mac package indices for apt, yum, and arch need their own GitHub Pages host.

Then there is the [shell plugin repo](https://github.com/dotsecenv/plugin). Plugin managers like oh-my-zsh and fish clone single repos. Package indexers like apt and yum do the same. None of them can fetch a subdirectory of a monorepo. So the plugin lives in its own repo, and the release pipeline pushes into it on every tag.

The pattern is the same for all three satellites: take the source-of-truth output (formula, package index, plugin code), write it into a satellite repo, sign the commit, push.

## What the first version looked like

The first version was a shell script. It generated a signing key, imported it on the runner, configured `git config user.signingkey`, ran `git commit -S`, then `git push`. The script also handled cleanup, key lifecycle, and a handful of corner cases that surfaced after the first few releases.

By the time it was reliable, it was about 150 lines. The signing key had to be a real secret with real lifecycle. We had to trust the runner with that secret for the duration of the job. Every new satellite repo meant another copy of the same shell to maintain.

GitHub signs the commits itself, attributed to a GitHub App. The runner holds an App credential; GitHub retains its commit-signing key. The [`createCommitOnBranch` GraphQL mutation](https://docs.github.com/en/graphql/reference/mutations#createcommitonbranch) creates each commit with that credential's owner as author and GitHub's signature.

Sounds great. The mutation is also where I lost most of two days.

## gh api -F lies about your JSON types

The natural way to call a GraphQL mutation from a shell script is `gh api graphql -F input=@file.json`, where `file.json` is your variables payload.

The `-F` flag has a footnote in the gh docs: it reads scalars and auto-detects type. The footnote does not mention that when you pass `@file.json`, gh reads the file as a single string and only auto-detects type at the top level, not inside the file. gh then silently sends every boolean and integer inside that file as a string.

The [`createCommitOnBranch`](https://docs.github.com/en/graphql/reference/mutations#createcommitonbranch) input schema has typed fields. Send one of those as a string when the schema expects a structured object and GitHub rejects the whole call:

```text
invalid value for type CreateCommitOnBranchInput!
```

The error message names the top-level input type, not the field that is actually wrong. Which makes the bug delightful to track down on a release-blocking workflow.

The workaround is straightforward once you find it. Build the request body yourself with `jq --slurpfile` so the types survive, then feed the resulting JSON as a single raw payload via `--input -`. That worked. It also added enough boilerplate that the script kept growing. The version that finally shipped was about 150 lines of shell and a mess to read.

## Extracting the custom GHA

A 150-line shell script that solves a recurring problem deserves to be its own artifact, not buried inside a release workflow. Other projects shipping to satellite repos also need verifiable commits without importing a commit-signing key, and face the same gh api stringification footgun.

I extracted the working version into [`releasetools/actions/signed-push`](https://github.com/releasetools/actions/tree/main/signed-push), a custom GitHub Action. The action takes a source directory, a target repo, a target branch, a commit body, and a token. It writes the directory into the satellite repo via [`createCommitOnBranch`](https://docs.github.com/en/graphql/reference/mutations#createcommitonbranch) and tags the commit. The caller never sees GraphQL.

The commit body uses [RFC-822 trailers](https://git-scm.com/docs/git-interpret-trailers) so the linkage to the source commit is both human-readable and machine-parseable:

```text
publish: v0.6.1

Source-Commit: dotsecenv/dotsecenv@21eee0028a7b8182e37cac526725b2fa9023d6e4
Source-SHA: 21eee0028a7b8182e37cac526725b2fa9023d6e4
Source-Path: packages
Source-Tag: v0.6.1
Published-By: https://github.com/dotsecenv/dotsecenv/actions/runs/26005850942
```

`Source-Commit` in `owner/repo@SHA` form gets auto-linked in the GitHub commit view, so the satellite commit always points back to the monorepo revision that produced it. `Source-SHA`, `Source-Path`, and `Source-Tag` are denormalized into separate trailers so downstream tooling can grep them out without parsing the compound form.

## What verification checks

The monorepo's `Verify Satellite Drift` workflow authenticates the exact plugin or packages commit before trusting its trailers. GitHub's API must report a valid signature made by GitHub, and the author must be `dotsecenv-automated-releases[bot]`. A Verified badge alone does not identify GitHub as the signer.

The verifier rejects ambiguous source trailers. `Source-Commit` and `Source-Path` must identify the expected monorepo and satellite directory. The source SHA must be reachable from monorepo `main`. On release publishes, `Source-Tag` must resolve to that SHA and be an annotated tag with a valid signature from the release maintainer, `MihaiBojin`. Ad-hoc publishes omit the tag and still undergo commit authentication and source ancestry checks.

Verifier code runs from a separate checkout of trusted monorepo `main`. Only after authentication does the workflow check out the claimed source revision for comparison. It compares file contents and executable bits, including symlink targets. For packages, it regenerates `retracted.txt` from the authenticated `go.mod` before comparing.

The packages satellite publishes only on explicit dispatch. A job without distribution secrets validates the dispatch actor and source provenance, then compares the mirrored files. Both secret-consuming jobs depend on that result. The build checks out the validated satellite commit, so a later push cannot change its inputs. The release App dispatches with an explicit source SHA; the maintainer can manually rebuild with `keep_versions` and authenticated HEAD trailers.

These checks trust the protected monorepo and its workflows. A credential that can replace the satellite workflow can also remove its checks. Commit provenance does not grant release authorization by itself; signed release tags supply that separate assertion.

## When this pattern is worth it

The signed-push pattern fits when all of these are true:

- You publish to one or more satellite repos on every release.
- You want commits in those repos to be signed and verifiable on GitHub.
- You want GitHub to hold the commit-signing key.
- The satellite repos are within or accessible to a GitHub App you control.

If your release flow already runs `git commit -S` with a hardware-backed key on a self-hosted runner you control, this rewrite buys you nothing. If you are doing key generation, GPG import, and key cleanup on hosted runners across multiple satellite repos, it deletes a lot of code and a lot of lifecycle complexity.

The [release workflow](https://github.com/dotsecenv/dotsecenv/blob/main/.github/workflows/release.yml) builds binaries with GoReleaser and publishes signed commits and version tags to the satellites. It dispatches packages publication and waits for the result. The org-scoped, sign-only `GPG_PRIVATE_KEY` and `GPG_PASSPHRASE` serve artifact and package metadata signing in the monorepo and packages workflows. The plugin satellite does not need those credentials.

And every release renders as one DAG you can read at a glance.
